# Mismo-Trainer — Data Model (v1 Snapshot)

**Status:** Verified against code — Hibernate mapping files, `hibernate.cfg.xml`, `src/db/*.sql`, and a real production dump (`src/db/db-dump-2024-04-05.sql`, captured 2024-02-05/2024-04-05) — plus bytecode inspection (`javap`) of the compiled `org.immregistries:mismo-match:1.1` dependency, which owns the actual entity classes (`org.immregistries.mismo.match.model.*`). This repo contains only the Hibernate `.hbm.xml` mapping files, not the entity source.

This document supersedes the "Verify in code" items in `mismo-conceptual-overview.md` §5, §17, §18, §22.

---

## 1. Engine and connectivity

- **Database:** MySQL 8, database name `matching_validation`, JDBC via `mysql-connector-java` (declared 8.0.30 in `pom.xml`, but `hibernate.cfg.xml`'s driver class is the older `com.mysql.jdbc.Driver`, not `com.mysql.cj.jdbc.Driver` — likely still works via the legacy driver shim, but is a mismatch worth cleaning up in v2).
- **ORM:** Hibernate 3.6 (Beta2) with `hibernate-annotations` 3.5.6 and `hibernate-c3p0` connection pooling, configured via classic XML `.hbm.xml` mapping files plus one central `hibernate.cfg.xml` — no annotation-based entities, no JPA.
- **⚠ Security finding:** `src/main/resources/hibernate.cfg.xml` and `src/db/create-user.sql` both contain a **plaintext database password committed to source control**, for a MySQL account (`mv_web`) granted `ALL PRIVILEGES ... WITH GRANT OPTION` on the whole database. This should be rotated and moved to an environment variable / secrets manager before any v2 work, and the credential should be treated as compromised since it has been in git history.
- **⚠ Security finding:** the `user` table stores passwords in **plaintext** (`varchar(30)`, e.g. the seed row's password is the literal word `welcome`), and `HomeServlet`'s login compares them with a raw HQL equality query (`from User where name = ? and password = ?`) — no hashing, salting, or rate limiting anywhere.

## 2. Tables

Five tables total. All five map 1:1 to Java classes that live in the `mismo-match-1.1.jar` dependency (package `org.immregistries.mismo.match.model`), **not** in this repo's `src/main/java`.

### 2.1 `patient` — defined but effectively unused

```
patient_id       int NOT NULL PRIMARY KEY   -- Hibernate generator="assigned" (app assigns IDs, no AUTO_INCREMENT)
name_first       varchar(100)
name_last        varchar(100)
name_middle      varchar(100)
name_suffix      varchar(100)
birth_date       varchar(100)   -- stored as a STRING, not a DATE/DATETIME column
grd_name_first   varchar(100)   -- guardian first name
grd_name_last    varchar(100)   -- guardian last name
mth_name_first   varchar(100)   -- mother's first name
mth_name_middle  varchar(100)
mth_name_maiden  varchar(100)   -- mother's maiden name
phone            varchar(100)
race             varchar(100)
ethnicity        varchar(100)
adr_street1      varchar(100)
adr_street2      varchar(100)
adr_city         varchar(100)
adr_state        varchar(100)
adr_zip          varchar(100)
gender           varchar(100)
birth_type       varchar(100)
birth_order      varchar(100)
mrns             varchar(100)   -- pipe-delimited list of MRNs, e.g. "5-V27|6-O47"
ssn              varchar(100)
medicaid         varchar(100)
shot_history     varchar(100)
```

**This table is empty in the production dump (0 rows).** Every patient record actually used by the app — the ~9,000 test-case patients, everything generated by `RandomServlet`/`RandomScriptServlet`, everything typed into `MatchPatientServlet` — is instead serialized as a comma-separated `key=value,key=value,...` string and stored inline in `match_item.patient_data_a` / `match_item.patient_data_b` (see §2.3). Only one address is representable here (`adr_*`), but the Java `Patient` model (see §4) actually supports **three** addresses (`address1`/`address2`/`address3`) plus vaccination fields (`VAC_NAME`, `VAC_DATE`, `VAC_CODE`, `VAC_MFR`) and a name alias — none of which this table has columns for. **Conclusion: the `patient` table is a vestigial/legacy structure that has been fully bypassed by the inline-serialized-string approach in practice.** A v2 data model should decide explicitly whether to normalize patient data into real columns/JSON or keep the inline string format — right now it's inline strings by default, with a dead normalized table sitting unused next to it.

### 2.2 `match_set` — the "training set" / "test set" concept

```
match_set_id  int NOT NULL PRIMARY KEY AUTO_INCREMENT
label         varchar(250) NOT NULL
update_date   datetime NOT NULL
```

Production data (4 rows): `'Test 2023'`, `'AIRA-A'`, `'PM Added'`, `'PM Added 2'`.

**This resolves the conceptual doc's open question directly: "training set" and "test set" are the exact same table and the exact same concept in the implementation — `match_set` is simply a named, flat, unordered bucket of `match_item` rows.** There is no separate "training set" entity, no versioning, no lock/finalize state, no parent/lineage, no notion of a set being "active" vs. "draft." A set is just a label plus a bag of test cases, and its only lifecycle field is `update_date` (bumped whenever any item is added/edited via `TestSetUploadServlet`).

### 2.3 `match_item` — a single labeled patient-pair test case

```
match_item_id   int NOT NULL PRIMARY KEY AUTO_INCREMENT
match_set_id    int NOT NULL              -- FK to match_set (not DB-enforced; app-level only)
label           varchar(250) NOT NULL
description     varchar(1000)
patient_data_a  text NOT NULL             -- serialized Patient A, "key=value,key=value,..."
patient_data_b  text NOT NULL             -- serialized Patient B, same format
expect_status   varchar(20) NOT NULL      -- "Match" | "Possible Match" | "Not a Match" | "Research" | "Not Sure"
user_id         int NOT NULL              -- FK to user (not DB-enforced)
update_date     datetime NOT NULL
data_source     varchar(120) NOT NULL     -- free-text provenance, e.g. a person's name or a generator tag
```

Production data: **~9,041 rows** across the 4 match_sets (row counts observed in the dump: 1648, 1651, 1648, 1737, 1653, 704 across six bulk `INSERT` statements).

**Label conventions observed in real data** (e.g. `S-1:ADDRESS_CHANGED:IDEAL-IDEAL`, `D-2:ADDRESS_CHANGED:IDEAL-GREATA`): `S-`/`D-` prefix (Same-patient / Different-patient scenario), a sequence number, a scenario code (`ADDRESS_CHANGED`, etc. — corresponds to a `Typest.Condition`), and a data-quality profile pair (`IDEAL`, `GREATA`, `GOODB`, `POOR`, etc. — corresponds to `Typest.Type`). This label scheme is produced by the synthetic generators (`RandomScriptServlet`, `RandomForCDCServlet`) documented in `trainer-pages.md` — bulk `match_item` data is generator output, hand-pasted/uploaded via `TestSetUploadServlet`, not hand-typed one row at a time.

`data_source` values observed include a person's name (e.g. `'Tesha'`) — this is attribution/provenance, not a system identifier.

**No DB-enforced foreign keys.** Both `match_set_id` and `user_id` are plain `int` columns with no `FOREIGN KEY` constraint in the DDL — referential integrity is entirely an application-level convention (Hibernate `many-to-one` mappings), not enforced by MySQL. A v2 schema should add real FKs.

### 2.4 `user` — attribution/login, not a real account system

```
user_id   int NOT NULL PRIMARY KEY AUTO_INCREMENT
name      varchar(30)
email     varchar(120)
password  varchar(30)   -- PLAINTEXT
```

Production data: **1 row** (the maintainer's own account). This is the entire "auth system" — see §1's security note. There's no role/permission field, so every logged-in user has identical (full) access to every page.

### 2.5 `configuration` — a persisted weight-set / Creature snapshot

```
configuration_id       int NOT NULL PRIMARY KEY AUTO_INCREMENT
world_name             varchar(250) NOT NULL
island_name            varchar(250) NOT NULL
generation              int NOT NULL
generation_score        double NOT NULL
generated_date           datetime NOT NULL
hash_for_signature      varchar(250) NOT NULL
configuration_script    text NOT NULL    -- the FULL weight-set YAML, verbatim (same format as Configuration.yml)
```

Production data: **1 row** (`world_name='Alma'`, `island_name='Alpha'`, `generation=1`, `generation_score=0`) — i.e., despite `generation` being present and indexed-looking, the production DB has essentially no meaningful optimization history captured centrally. This matches a finding in `optimization-and-islands.md`: the central sync protocol **overwrites the latest row per (world, island) in place** rather than inserting a new row per generation, so history is lost by design, not just by light usage.

This table is where a "weight set" (§17 of the conceptual doc) actually lives: **the entire configuration is one opaque YAML blob in `configuration_script`.** The indexed columns (`world_name`, `island_name`, `generation`, `generation_score`, `generated_date`, `hash_for_signature`) exist purely so the app can find/sort/identify a blob without parsing it — none of the individual detector/signal weight values are queryable as columns. There is no explicit "status" field (draft/active/production), no parent/ancestor configuration_id, and no way to mark a configuration as "the one currently in production use" — promotion/activation is not a modeled concept anywhere in this schema (confirmed also in the servlet review — see `trainer-pages.md` §`GenerateWeightsServlet`).

## 3. `upgrade-1.1.sql` — what changed between schema versions

The only migration script present adds the entire `configuration` table (it doesn't exist in `initial.sql`'s snapshot). In other words, the "1.1" schema bump was solely about introducing persisted weight-set storage — everything else (`patient`, `match_set`, `match_item`, `user`) has been stable since `initial.sql`. There is no migration-versioning table (e.g. no `schema_version`) — schema evolution is tracked only by the existence of ad hoc `upgrade-*.sql` files in `src/db/`, applied manually.

## 4. The real "Patient" data model (resolves conceptual doc §5)

The conceptual doc speculates a patient record might be "a hash-map of named values" with an open field set. **Verified in code (via `javap` on `org.immregistries.mismo.match.model.Patient`): it is a fixed, strongly-typed field set with named getters/setters, backed internally by a generic `Map<String,String> valueMap`** — so conceptually it *is* a map under the hood (and `getValue(String)`/`setValue(String,String)` generic accessors do exist), but every field Mismo actually knows how to detect on is a compiled-in `public static final String` constant with a matching typed getter/setter. Practically: you can stuff arbitrary extra keys into the map via `setValue()`, but no detector will ever look at a key that isn't one of the constants below, so it behaves as a fixed schema for matching purposes even though the storage is a map.

**Full field list** (from `Patient`'s static constants):

| Category | Fields |
|---|---|
| Name | `NAME_FIRST`, `NAME_MIDDLE`, `NAME_LAST`, `NAME_LAST_HYPH` (hyphenated-last-name variant), `NAME_SUFFIX`, `NAME_ALIAS` |
| Birth | `BIRTH_DATE`, `BIRTH_STATUS`, `BIRTH_TYPE`, `BIRTH_ORDER` |
| Guardian / parent | `GUARDIAN_NAME_FIRST`, `GUARDIAN_NAME_LAST`, `MOTHER_NAME_FIRST`, `MOTHER_NAME_LAST`, `MOTHER_NAME_MIDDLE`, `FATHER_NAME_FIRST`, `FATHER_NAME_LAST`, `MOTHER_MAIDEN_NAME` |
| Contact | `PHONE` |
| Demographics | `GENDER`, `RACE`, `ETHNICITY` |
| Identifiers | `MRNS` (pipe-delimited list), `SSN`, `MEDICAID` |
| Address (×3) | `ADDRESS_STREET1`/`_ALT`, `ADDRESS_STREET2`, `ADDRESS_CITY`, `ADDRESS_STATE`, `ADDRESS_ZIP`, and the same six fields again prefixed `ADDRESS_2_*` and `ADDRESS_3_*` — i.e. **three full addresses per patient**, exposed as three parsed `Address` objects (`getAddress1()`/`getAddress2()`/`getAddress3()`) |
| Immunization | `SHOT_HISTORY`, `VAC_NAME`, `VAC_DATE`, `VAC_CODE`, `VAC_MFR` |

Every field is a plain `String` — dates (`BIRTH_DATE`) are stored/compared as strings (e.g. `"20071225"`), not parsed `Date` objects, at the `Patient` level (contrast with `PatientCompare`, which does hold a `java.util.Date born` for its own use). Missing data is represented as `null`/empty string, never a separate "unknown" sentinel — consistent with the conceptual doc's "missing data is normal" principle (§25.2).

**Address parsing:** the `Address` model (`org.immregistries.mismo.match.model.Address`) does real tokenization on `line1`/`line2` — it separates `number`, `streetName`, `apartment`, classifies `addressType`, and recognizes floor/apartment/PO-box token patterns (`FIRST_FLOOR_TOKEN`, `SECOND_FLOOR_TOKEN`, `APARTMENT_TOKENS`, `PO_BOX_TOKEN`) and a list of known-invalid ZIP codes — this is nontrivial parsing logic living entirely in the compiled `mismo-match` jar, not visible as source in this repo.

## 5. Open questions / gaps for v2 design

- Should the `patient` table be revived (normalized storage) or should the inline-serialized-string approach in `match_item` be formalized (e.g. as JSON) as the intentional design? Right now v1 has both, with one dead.
- No FK constraints anywhere — worth adding in v2 regardless of ORM choice.
- No status/lifecycle modeling for `match_set` (draft/reviewed/locked) or `configuration` (draft/candidate/production) — both are flagged as needed in the conceptual doc's modernization goals (§24.3) and confirmed absent here.
- No versioning/history for `configuration` rows — each (world, island) pair's row is overwritten in place by the sync protocol (see `optimization-and-islands.md`).
- `user` table has no role/permission concept — anyone who can log in has full access to every page and every match_set/configuration.
